# 채팅 기능 재설계 방향 (DBML 이전 설계서)

대상: 채팅 테이블만 신규/수정. `gathering`, `users`, `gathering_recommendation`(AI) 등 다른 테이블은 **FK 참조만** 하고 스키마는 건드리지 않는다.
근거 자료: 채팅 UI 시안(방 목록·공지·읽음 표시·AI 추천 카드), `채팅.txt`(활동 온도 기능).

---

## 0. 설계 원칙 (확장성의 핵심)

> **DB는 "영속 상태의 단일 진실원본"만 담고, 실시간·확장 레이어(WebSocket/Redis/Kafka)는 그 위에 얹는다.**
> 그래서 나중에 WS/Redis/Kafka를 붙여도 스키마 마이그레이션이 거의 없도록, 아래 4가지를 **지금 미리** 넣는다.

1. **메시지 id는 bigint 단조 증가** + `created_at` 인덱스 → 정렬·커서 페이징·"읽은 지점" 비교가 전부 id 하나로 해결.
2. **`client_message_id`(uuid) 컬럼** → 소켓 재전송/중복 방지(멱등성). 나중에 WS 붙일 때 컬럼 추가 마이그레이션을 안 하려고 지금 넣는다.
3. **비정규화 캐시**(`chat_room.last_message_*`) → 방 목록/미리보기를 매번 집계하지 않음.
4. **`meta` JSONB 컬럼**(message, 추천카드) → 새 메시지 종류·카드 필드가 생겨도 컬럼 추가 없이 흡수.

이 4개가 "확장 시 DB 수정 최소화" 요구의 실제 답이다. 상세는 7장.

---

## 1. 핵심 테이블 재설계 (기능 → 구조 매핑)

### chat_room (수정)
방 하나의 메타. 시안의 "그룹 채팅 / 1:1 채팅"을 위해 타입을 확장한다.

- `type`: **GROUP / DIRECT / QUICK_CONNECT** (기존 GROUP·QUICK_CONNECT에 1:1용 DIRECT 추가)
- `gathering_id` (nullable, unique): 모임 자동 생성 방 연결. DIRECT·QUICK_CONNECT는 NULL
- `title` (nullable): 표시명. GROUP은 모임 제목 스냅샷, DIRECT는 상대 이름을 앱에서 계산
- **`last_message_id`, `last_message_at`** (비정규화 캐시): 최근 채팅방 조회·마지막 메시지 미리보기·최근순 정렬
- `closed_at` (nullable): QUICK_CONNECT 종료(대화 종료 시 자동 삭제 정책과 연결)
- `created_at`

→ 커버: **모임 생성 시 자동 채팅방 생성**(gathering confirm에서 GROUP+gathering_id 생성), **마지막 메시지 조회**, **최근 채팅방 조회**.

### chat_room_member (수정)
누가 어느 방에 있고 어디까지 읽었는지.

- `chat_room_id`, `user_id`, `role`(OWNER/MEMBER — 공지 작성 권한 구분)
- **`last_read_message_id`** (nullable): 읽음 처리·안읽음 수 계산의 기준
- `joined_at`, **`left_at`** (nullable): 채팅방 나가기(소프트). NULL이면 현재 참여 중
- (선택) `notification_enabled`: 방별 알림 on/off
- unique(chat_room_id, user_id)

→ 커버: **채팅방 참가자 관리**, **채팅방 나가기**, **읽음 처리 / 마지막 읽은 메시지**.

### message (수정)
- `chat_room_id`, `sender_id` (nullable = SYSTEM)
- `type`: **TEXT / IMAGE / SYSTEM**
- `content` (text): 텍스트 본문. (이미지 URL을 여기 넣지 않음 — 아래 attachment로 분리)
- **`meta` JSONB** (nullable): SYSTEM 메시지 상세(입장/퇴장/모임확정 등 종류+파라미터), 카드 공유 참조 등 확장 흡수
- **`client_message_id`** (uuid, nullable, unique per room): 멱등 전송
- **`deleted_at`** (nullable): 메시지 소프트 삭제("삭제된 메시지입니다")
- `created_at`(=sent_at), 인덱스 `(chat_room_id, id)`

→ 커버: **시스템 메시지**(type=SYSTEM + meta), **이미지 메시지**(type=IMAGE + attachment), 메시지 삭제, 커서 페이징.

### message_attachment (신규)
이미지/파일 메타를 별도 분리(다중 첨부·썸네일·용량 대응).

- `message_id`, `file_url`, `thumbnail_url`, `content_type`, `size`, `width`, `height`, `sort_order`

→ 커버: **이미지 메시지**(시안의 파일첨부 아이콘). 지금은 이미지 1장이라도, 겸용 content 문제를 없애고 확장 대비.

### chat_notice (신규) — 공지
시안 상단의 고정 공지(📢). 방마다 공지 이력을 두되 현재 활성 공지 1건.

- `chat_room_id`, `message_id`(nullable, 공지로 고정한 메시지 참조) 또는 `content`, `created_by`, `is_active`, `created_at`
- 활성 공지만 유일: 부분 유니크(`WHERE is_active`)

→ 커버: **공지**. (대안: message.type에 NOTICE + `chat_room.pinned_message_id`. 이력 관리를 원하면 별도 테이블이 깔끔.)

## 2. 읽음 / 마지막 메시지 / 최근 방 — 처리 방식

- **안읽음 수** = `count(message where chat_room_id=? and id > last_read_message_id)`. 방 단위 포인터 하나로 계산 → 시안 좌측 방 목록 배지에 충분.
- **1:1 읽음(✓✓)** = 상대 멤버의 `last_read_message_id >= 내 메시지 id` 이면 읽음. 별도 read 테이블 없이 처리.
- **단체방 "N명 읽음"이 꼭 필요하면** → `message_read(message_id, user_id, read_at)` 신규. 단, 메시지×인원만큼 행이 폭증하므로 MVP에선 last_read 포인터만 권장(트레이드오프 명시).
- **최근 방 목록** = `chat_room_member(user_id, left_at IS NULL)` → `chat_room` 조인 → `order by last_message_at desc`. last_message 캐시 덕에 message 집계 불필요.

---

## 3. 시스템 메시지 & 공지 표현

- 입장/퇴장/모임 확정/공지 등록 같은 이벤트 = `type=SYSTEM`, `sender_id=NULL`, `meta`에 `{ "systemType": "MEMBER_JOINED", "userId": 12 }` 형태로 저장 → 프론트가 meta로 문구 렌더. **enum 추가 없이 종류 확장**(JSONB의 이점).
- 공지는 chat_notice로 고정 + 알림용으로 SYSTEM 메시지 1건 발행(시안처럼 상단 고정 + 채팅 흐름에도 표시).

## 4. AI 추천 활동 (우측 패널) — 채팅 소유 테이블로 분리

기존 `gathering_recommendation`(모임 추천)과 **역할이 다름**(방 안에서의 활동 카드). 다른 테이블 수정 없이 채팅 쪽에 신규로 둔다.

### chat_activity_recommendation (신규)
방에 노출되는 AI 추천 활동 카드("보드게임 카페 투어", 아이스브레이킹 미션 등).

- `chat_room_id`, `title`, `description`, `meta` JSONB(카드 세부·미션 목록·이미지), `round_no`(회차), `created_at`

### chat_activity_interaction (신규) — 클릭/공유/저장 기록 통합
"추천 클릭 기록"·"채팅방 공유"·"저장"을 **이벤트 로그 한 테이블**로 통합(분석·Kafka 친화).

- `recommendation_id`, `user_id`, `chat_room_id`, `type`: **IMPRESSION / CLICK / SHARE / SAVE**, `created_at`

→ **추천 클릭 기록** = CLICK 행, **채팅방 공유** = SHARE 행(+ 아래 메시지 발행), **저장** = SAVE 행.

### saved_activity (신규, 선택)
"AI가 추천한 활동 저장"의 **저장 목록 화면**이 필요하면 조회 최적화를 위해 별도.

- `user_id`, `recommendation_id`, `saved_at`, unique(user_id, recommendation_id)
- (목록 화면이 없고 통계만이면 생략하고 interaction의 SAVE로 대체 가능)

### 채팅방 공유의 실제 저장
"채팅방에 공유" 클릭 → 방에 **메시지 1건**을 발행하되 `type=SYSTEM`(또는 별도), `meta`에 `{ "kind":"ACTIVITY_CARD", "recommendationId": 33 }`. 새 메시지 종류를 위한 컬럼/enum 추가 없이 JSONB로 흡수 → **DB 수정 최소화 원칙과 일치**.

---

## 5. 채팅방 활동 온도 (채팅.txt)

AI 분석이 아니라 **최근 7일 메시지 수 기반 통계**.

- 기본: 온디맨드 집계 `count(message where room=? and created_at > now-7d)`. 데이터 적을 땐 이걸로 충분.
- 확장: **`chat_room_daily_stat(chat_room_id, stat_date, message_count)`** 롤업 테이블(신규, 선택) → 잔디 시각화 + 온도 계산을 값 조회로 대체. Kafka 컨슈머/배치가 채워 넣음(7장 연계).

## 7. 확장성 설계 — WebSocket / Redis / Kafka 도입 시 DB 최소 변경

### 전제: 지금 넣어두는 "미래 대비 최소 장치" 4종
`client_message_id`(멱등), `last_message_*`(목록 캐시), `meta` JSONB(스키마 흡수), 그리고 **아웃박스 테이블 1개**(아래). 이 4개만 있으면 WS/Redis/Kafka는 스키마를 거의 안 건드리고 얹힌다.

### WebSocket / STOMP
- 구조: 클라이언트 ↔ STOMP 엔드포인트. 메시지는 **먼저 DB 저장 → 그다음 브로드캐스트**(저장이 진실원본, 소켓은 전달만).
- DB 변경: **없음**. 정렬/재조회는 bigint id + created_at로 이미 가능. 재전송 중복은 `client_message_id`로 차단.
- 서버 다중화 시 단일 서버 브로커로는 팬아웃 한계 → Redis(아래)로 확장.

### Redis
DB를 건드리지 않고 **휘발성/캐시성 상태**를 전부 Redis로 뺀다. 이게 스키마 안정성의 핵심.
- **Pub/Sub**: WS 서버 여러 대 간 메시지 팬아웃(멀티 인스턴스). DB 무관.
- **캐시**: 안읽음 수·최근 방 목록·last_read를 Redis에 캐시(원본은 DB). 부하 분산.
- **Presence/typing/온라인 표시**: **오직 Redis만**. DB에 절대 넣지 않음 → 스키마 churn 방지.
- **QUICK_CONNECT 일회성**: 시안의 "코드 일회성, 대화 종료 시 자동 삭제"는 Redis TTL과 궁합이 좋다. 코드·세션·(원하면)메시지를 TTL로 Redis에 두고 만료 시 자동 소멸 → DB 보존/삭제 잡 부담을 없앤다. (영구 보관이 필요 없으면 quick-connect 메시지를 DB에 안 남기는 선택도 가능.)

### Kafka
- 용도: `message.created`, `message.read`, `activity.clicked` 같은 이벤트를 발행 → **푸시 알림, 활동 온도 롤업, AI 파이프라인, 분석**이 비동기 컨슈머로 각자 소비.
- DB 최소 변경의 정석 = **트랜잭션 아웃박스 패턴**: 메시지 저장 트랜잭션에서 **`chat_outbox_event(id, aggregate_type, aggregate_id, event_type, payload JSONB, created_at, published_at)`** 에도 같이 INSERT → 릴레이가 Kafka로 발행. 이 아웃박스 테이블 **하나만** 지금 만들어두면, 이후 어떤 이벤트/컨슈머가 늘어도 코어 테이블(message 등) 스키마는 그대로다.
- 활동 온도(`chat_room_daily_stat`)와 알림은 이 이벤트 스트림의 컨슈머로 자연스럽게 붙는다.

### 요약: "확장해도 DB 안 바뀜"의 실체
휘발성 상태 → Redis, 이벤트 전파 → Kafka(아웃박스), 신규 필드 → JSONB `meta`, 멱등/정렬 → id·client_message_id. **영속 테이블은 위 6장 세트에서 거의 고정**된다.

## 8. 레퍼런스 아키텍처 & 연동 방향 (텔레그램·기존 솔루션)

요청하신 "이미 나와 있는 레포 / 텔레그램 연결" 관점의 방향 제시.

### (A) 우리 스택에 가장 잘 맞는 지름길 — Supabase Realtime
이미 **Supabase Auth**를 쓰고 있으니, 자체 WS 서버를 세우기 전에 **Supabase Realtime**(Postgres 변경을 논리복제로 구독→WebSocket 브로드캐스트)을 검토할 가치가 크다. `message` INSERT를 그대로 실시간 구독 → 초기 인프라 최소. 트래픽이 커지면 STOMP+Redis 자체 구축으로 이전. **DB 스키마 변경 없이** 실시간을 얻는 가장 빠른 길.

### (B) Spring 표준 경로 (자체 구축)
`spring-boot-starter-websocket` + STOMP + 내장 SimpleBroker로 시작 → 스케일아웃 시 **외부 브로커 릴레이**(RabbitMQ STOMP 또는 Redis)로 교체. 애플리케이션 코드는 유지, 브로커만 바꾸는 구조라 이전 비용이 낮다.

### (C) 오픈소스에서 빌려올 패턴 (통째 도입이 아니라 설계 참고)
- **Mattermost / Rocket.Chat**(둘 다 self-host 채팅): 채널-멤버-포스트 3분할, last_viewed(우리 last_read와 동일 개념), 시스템 포스트를 props(JSONB)로 확장 — 우리 `meta` 설계와 같은 방향. 스키마 참고용으로 좋다.
- **Telegram(MTProto) 교훈**: 대화별 단조 증가 시퀀스(pts)와 "여기까지 읽음(read_inbox_max_id)" 포인터. 우리의 bigint message id + `last_read_message_id`가 정확히 같은 아이디어 → 이 방향이 검증된 설계임을 뒷받침. MTProto 프로토콜 자체를 도입하란 뜻은 아님.

### (D) "텔레그램 연결" = 알림 브리지 옵션
텔레그램을 **또 하나의 알림 채널**로 붙이는 방향. 7장의 아웃박스/Kafka 이벤트 스트림에 **Telegram Bot API로 포워딩하는 컨슈머**를 하나 추가하면, 새 메시지·공지를 사용자의 텔레그램으로도 발송할 수 있다. 핵심은 **채팅 코어와 분리된 컨슈머**라서 DB·전송 로직을 안 건드린다는 점(원한다면 사용자별 telegram_chat_id 매핑 테이블 1개만 추가). 데모/해커톤에서 "실시간 알림"을 싸게 보여주기 좋은 카드.

### 권장 로드맵
1단계(MVP): REST + 커서 페이징 + (A)Supabase Realtime 또는 (B)STOMP SimpleBroker.
2단계: Redis(팬아웃·프레즌스·캐시·QUICK_CONNECT TTL).
3단계: Kafka(아웃박스) + 알림/활동온도 컨슈머, 필요 시 (D)텔레그램 브리지.
→ 각 단계에서 **영속 스키마는 6장 세트 그대로.**
