## 0. 핵심 변경 (요약)

> **기존안**: 채팅을 텔레그램으로 대체.
> **변경안**: **채팅은 WebSocket으로 자체 구현**하고, **텔레그램은 채팅이 아니라 알림(Notification) 용도로만** 사용한다.

이유: 텔레그램 채팅은 유저가 앱 밖으로 이탈하고, 우리 핵심 기능(AI 추천 카드 공유·모임 자동 채팅방·잔디/캔버스)을 엮을 수 없음. 자체 채팅이어야 서비스가 완결됨. 텔레그램은 알림 푸시 채널로만 활용.

아키텍처:

```
                 React
                   │
        REST API + WebSocket
                   │
              Spring Boot
   ┌───────────────┬────────────────┐
Chat Service    AI Service    Notification Service
   │               │                │
PostgreSQL     OpenAI API      Telegram Bot API
(자체 채팅)     (주제/미션 추천)   (+ 인앱 알림)
```

## 1. 배경

모임 기능에 이어 채팅 기능을 구현하기 위해, 실서비스(Discord·Slack·카카오톡·오픈채팅) 사례를 참고하여 채팅 테이블 구조를 확정함. **기존 테이블(users, gathering, AI 추천 등)은 수정하지 않고**, 채팅·알림 테이블만 신규 추가·설계하는 것을 원칙으로 함.

## 2. 핵심 결정사항 (요약)

| # | 결정 | 내용 |
|---|---|---|
| 1 | 범위 원칙 | 채팅·알림 테이블만 신규/수정. 외부 테이블은 id로 **참조만**, 절대 수정 안 함 |
| 2 | 방 종류 | `chat_room.type` = GROUP / DIRECT(1:1) / QUICK_CONNECT(안심커넥트) |
| 3 | 자동 생성 | 모임 확정 시 GROUP 채팅방 + 참여자 자동 등록 |
| 4 | 읽음 처리 | 방의 `last_message_id` vs 멤버의 `last_read_message_id` 비교로 계산 |
| 5 | 나가기 | `left_at` 소프트 처리(이력 보존) |
| 6 | 시스템 메시지 | `type=SYSTEM`, 보낸사람 NULL |
| 7 | 공지 | `chat_notice` 테이블, 방당 활성 공지 1건 |
| 8 | 이미지 | `message_attachment` 테이블(썸네일·다중 대응) |
| 9 | 최근 방/마지막 메시지 | `chat_room.last_message_*` 캐시로 목록 정렬·미리보기 |
| 10 | AI 확장 대비 | 메시지 `type`에 **CARD** + `meta`(JSONB). AI 원본 테이블은 나중에 별도 추가 |
| 11 | 채팅 실시간 | **자체 WebSocket(STOMP)** 으로 구현. 텔레그램 채팅 안 씀 |
| 12 | 알림 | `notification`(인앱 알림함) + **텔레그램 봇(연결 사용자)** 발송. 독립 도메인, 이벤트 기반 |

## 3. 필수 기능 → 구조 매핑

요구된 필수 기능 전부를 아래 구조로 커버함.

- 그룹채팅 / 모임 생성 시 자동 채팅방 → `chat_room`(type·gathering_id)
- 참가자 관리 / 채팅방 나가기 → `chat_room_member`(role·left_at)
- 읽음 처리 / 마지막 읽은 메시지 → `last_read_message_id`
- 마지막 메시지 / 최근 채팅방 조회 → `chat_room.last_message_*`
- 시스템 메시지 → `message`(type=SYSTEM)
- 공지 → `chat_notice`
- 이미지 메시지 → `message_attachment`

## 4. AI 기능 확장 대비 (지금은 구현 안 함)

향후 추가될 AI 기능(대화 주제 추천·미션 추천·콘텐츠 추천)은 **모두 "카드"를 만들어 채팅방에 공유하는 형태**로 정리됨. 이를 위해 지금은 훅만 심어둠.

- 공유된 카드는 `type=CARD` 메시지 1건으로 저장 → 실시간·읽음·페이징을 기존 경로로 재사용
- 카드 데이터·종류는 `meta`(JSONB)에 담아 **DB 변경 없이 확장**
- AI 추천 원본·클릭/저장 통계는 나중에 **새 테이블**로 붙이며, 채팅 코어는 안 건드림

## 5. 알림 (인앱 + 텔레그램)

- 채팅 새 메시지 배지는 **기존 읽음 포인터 + WebSocket**으로 처리(별도 비용/테이블 없음)
- 신청·수락·확정·공지 같은 이벤트성 알림은 `notification` 테이블에 저장(인앱 알림함)
- 각 도메인은 이벤트만 발행, `NotificationService`가 저장·발송 → **결합도 0**
- 발송 경로: **인앱(WebSocket) + 텔레그램 봇**. 텔레그램은 `user_telegram`으로 연결한 사용자에게만 발송
  - ⚠️ 텔레그램 봇은 **사용자가 먼저 봇을 시작(연결)해야** 발송 가능 → "텔레그램 연결" 설정 단계 필요. 미연결자는 인앱 알림만 수신
- **금전 비용 0** (텔레그램 봇 API 무료)

## 6. 확장성 (WebSocket / Redis / Kafka)

채팅 실시간은 **자체 WebSocket(STOMP)** 으로 구현하며, 확장 시에도 **DB 스키마 변경이 최소화**되도록 설계함.

- 시작: STOMP 내장 브로커 → 스케일아웃 시 **Redis(STOMP relay/pub-sub)** 로 팬아웃
- 휘발성 상태(프레즌스·타이핑·안읽음 캐시·QUICK_CONNECT 일회성) → **Redis**(DB에 안 넣음)
- 이벤트 전파(알림·활동온도·AI) → **Kafka + 아웃박스 패턴**
- 미리 심은 장치: `meta`(JSONB) 확장, `client_message_id`(멱등), `last_message_*`(목록 캐시)

## 8. 추가 논의 / 결정 필요 사항

- 참가 신청 **재신청 정책**(거절 후 재신청 허용 여부 → 유니크 제약 방식 결정)
- 단체방 **개별 읽음 표시**("N명 읽음") 필요 여부 (MVP는 방 단위 포인터만)
- **QUICK_CONNECT 메시지 보존 정책**(종료 시 삭제 vs 보관)
- 실시간 구현 방식 최종 선택(Supabase Realtime vs 자체 STOMP)
