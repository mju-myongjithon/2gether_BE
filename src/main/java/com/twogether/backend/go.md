채팅방 활동 온도 및 날짜별 대화 잔디 기능을 구현해주세요.

현재 채팅 기능이 다른 팀원에 의해 구현된 상태입니다.
기존 채팅 구조를 먼저 충분히 분석하고, 기존 기능을 불필요하게 수정하거나
리팩터링하지 않은 상태에서 조회·집계 기능만 최소 범위로 추가해주세요.

이번 기능은 AI 기능이 아닙니다.
채팅 내용을 분석하거나 외부 AI 서버로 전송하지 않고,
메시지 개수만 집계하여 채팅방 활동성을 보여주는 기능입니다.

==================================================
1. 기능 목표
   ==================================================

모임 페이지에서 해당 채팅방의 활동성을 확인할 수 있도록 다음을 제공합니다.

1. 최근 7일간 메시지 수
2. 최근 7일 메시지 수에 따른 활동 상태
3. 최근 30일간 날짜별 메시지 수
4. 날짜별 메시지 수를 프론트에서 잔디 형태로 표시할 수 있는 level

처리 예시:

- 최근 대화가 많음 → 활동 상태 높음
- 최근 대화가 적음 → 활동 상태 낮음
- 대화가 없음 → 비활성
- 날짜별 메시지 개수에 따라 잔디 색상 진하기 변경

==================================================

   ==================================================

- 기존 채팅 Controller, Service, Repository, Entity 구조를 먼저 분석할 것
- 기존 채팅 전송, 조회, 읽음 처리 기능을 변경하지 말 것
- 기존 API 경로나 메서드 시그니처를 임의로 변경하지 말 것
- 채팅 기능과 관련 없는 패키지를 수정하지 말 것
- 기존 테스트를 삭제하거나 약화하지 말 것
- 새로운 공통 응답 구조를 만들지 말 것
- 기존 ApiResponse, BusinessException, ErrorCode,
  GlobalExceptionHandler를 재사용할 것
- SecurityConfig를 임의로 변경하지 말 것
- WebSocket 전송 구조를 수정하지 말 것
- Message 엔티티에 새로운 통계 필드를 추가하지 말 것
- 새로운 DB 테이블을 만들지 말 것
- AI Client, FastAPI, LLM 호출을 추가하지 말 것
- 모든 메시지를 애플리케이션 메모리로 불러와 계산하지 말 것
- DB 집계 쿼리를 사용하여 필요한 데이터만 조회할 것
- 다른 팀원이 만든 채팅 코드를 불필요하게 정리하거나 리팩터링하지 말 것

주요 변경 범위는 다음으로 제한해주세요.

- 채팅 활동 조회용 Controller 또는 기존 ChatRoomController의 최소 메서드
- 채팅 활동 조회용 Service
- MessageRepository의 최소 집계 쿼리
- 응답 DTO
- 관련 테스트

==================================================
3. API
   ==================================================

API:

GET /api/chat-rooms/{chatRoomId}/activity

이 API는 특정 채팅방의 최근 활동 통계를 반환합니다.

요청 Body는 없습니다.

JWT 인증이 필요하며,
현재 로그인한 사용자가 해당 채팅방의 현재 참여자일 때만 조회 가능해야 합니다.

기존 ChatRoomMemberRepository 또는 채팅방 참여자 검증 로직이 있다면
새로 만들지 말고 반드시 재사용해주세요.

나간 사용자(leftAt 값이 존재하는 사용자)를 현재 참여자로 인정할지는
기존 채팅방 접근 정책을 그대로 따르세요.

==================================================
4. 메시지 집계 기준
   ==================================================

메시지 개수는 다음 기준으로 집계해주세요.

포함:

- TEXT
- IMAGE
- CARD
- 실제 사용자가 보낸 메시지

제외:

- SYSTEM 메시지
- deletedAt이 null이 아닌 삭제된 메시지
- 조회 기간 밖의 메시지

날짜 기준:

- Message.createdAt
- Asia/Seoul 시간대 기준

기간 범위는 반개방 범위를 사용해주세요.

예:

[startDate 00:00 Asia/Seoul, nextDate 00:00 Asia/Seoul)

서버 기본 시간대에 의존하지 말고
Asia/Seoul을 명시적으로 사용해주세요.

==================================================
5. 최근 7일 활동 온도
   ==================================================

최근 7일은 서울 기준 오늘을 포함합니다.

예:

- 오늘이 2026-07-17이라면
- 2026-07-11 00:00 이상
- 2026-07-18 00:00 미만

최근 7일 메시지 수를 recent7DaysMessageCount로 반환해주세요.

활동 상태 Enum 또는 문자열:

- INACTIVE
- LOW
- MEDIUM
- HIGH

MVP 기준 임시 정책:

- 0개 → INACTIVE
- 1~9개 → LOW
- 10~29개 → MEDIUM
- 30개 이상 → HIGH

활동 상태 계산은 Controller가 아니라 Service 또는 별도 명확한 메서드에서 처리해주세요.

프론트에서 자유롭게 표시할 수 있도록 온도 숫자보다 상태값을 우선 반환해주세요.

필요하다면 activityScore를 함께 제공할 수 있지만,
불필요한 계산이라면 추가하지 마세요.

==================================================
6. 최근 30일 대화 잔디
   ==================================================

최근 30일은 서울 기준 오늘을 포함합니다.

- startDate = 오늘 - 29일
- endDate = 오늘
- 총 30일

활동이 없는 날짜도 반드시 포함하고,
날짜 오름차순으로 정확히 30개를 반환해주세요.

날짜별 데이터:

- date
- messageCount
- level

잔디 level 기준:

- 0개 → level 0
- 1~4개 → level 1
- 5~9개 → level 2
- 10~19개 → level 3
- 20개 이상 → level 4

색상값과 HEX 코드는 백엔드에서 반환하지 마세요.
프론트가 level에 따라 색상을 정합니다.

7. 응답 DTO
   ==================================================

권장 응답 예시:

{
"success": true,
"message": "채팅방 활동 통계 조회에 성공했습니다.",
"data": {
"chatRoomId": 1,
"recent7DaysMessageCount": 24,
"activityStatus": "MEDIUM",
"startDate": "2026-06-18",
"endDate": "2026-07-17",
"dailyActivities": [
{
"date": "2026-06-18",
"messageCount": 0,
"level": 0
},
{
"date": "2026-07-17",
"messageCount": 8,
"level": 2
}
]
}
}

권장 DTO:

ChatRoomActivityResponse

- Long chatRoomId
- long recent7DaysMessageCount
- ChatActivityStatus activityStatus
- LocalDate startDate
- LocalDate endDate
- List<ChatDailyActivityResponse> dailyActivities

ChatDailyActivityResponse

- LocalDate date
- long messageCount
- int level

기존 DTO 스타일이 record라면 record를 사용하고,
class 기반이면 기존 스타일을 따르세요.

8. Repository
   ==================================================

기존 MessageRepository를 먼저 확인해주세요.

필요한 조회 기능:

1. 특정 채팅방의 최근 7일 메시지 수
2. 특정 채팅방의 최근 30일 메시지 생성 시각 또는 날짜별 개수

조건:

- chatRoomId 일치
- deletedAt is null
- type != SYSTEM
- createdAt 기간 조건

권장 방식:

- 최근 7일 수는 DB count 쿼리
- 최근 30일 잔디는 날짜별 GROUP BY 쿼리 또는 createdAt projection 조회
- 전체 Message 엔티티 및 content를 불러오지 말 것
- 메시지 본문은 이 기능에서 절대 조회하지 말 것

JPQL 날짜 GROUP BY가 시간대 처리상 불안정하면,
최근 30일 범위의 createdAt만 projection으로 조회한 뒤
Service에서 Asia/Seoul LocalDate로 변환하여 그룹화해도 됩니다.

다만 다음 데이터는 조회하지 마세요.

- 메시지 content
- meta
- attachment
- sender 전체 엔티티

채팅 내용 자체는 활동 통계에 필요하지 않습니다.

==================================================
9. 권한 검증
   ==================================================

요청 사용자가 채팅방 멤버인지 확인해주세요.

처리 흐름:

1. JWT subject로 현재 User 조회
2. chatRoomId로 채팅방 존재 여부 확인
3. 기존 채팅방 참여자 검증 로직 재사용
4. 참여자가 아니면 403
5. 통계 조회
6. ApiResponse 반환

기존 ChatRoom 조회 및 멤버 검증 Service가 있다면
중복 로직을 새로 작성하지 마세요.

필요한 ErrorCode 예시:

- CHAT_ROOM_NOT_FOUND
- CHAT_ROOM_ACCESS_DENIED

이미 동일한 ErrorCode가 있다면 반드시 재사용하세요.

GlobalExceptionHandler는 수정하지 마세요.

10. 시간 처리
    ==================================================

모든 날짜 계산은 Asia/Seoul 기준으로 처리해주세요.

가능하면 테스트 안정성을 위해 Clock을 생성자 주입해주세요.

기존 프로젝트에 이미 Clock Bean이 있다면 반드시 재사용하세요.

Campus Canvas 구현에서 Clock Bean이 이미 추가되어 있다면
새 Clock Bean을 중복 생성하지 말고 기존 Bean을 재사용해주세요.

12. 테스트
    ==================================================

기존 채팅 테스트를 수정하거나 삭제하지 말고
새 테스트를 추가해주세요.

최소 테스트:

1. 채팅방 참여자의 정상 조회
2. 비참여자의 조회 실패
3. 존재하지 않는 채팅방 조회 실패
4. 최근 7일 메시지만 집계
5. 7일 범위 밖 메시지 제외
6. 삭제된 메시지 제외
7. SYSTEM 메시지 제외
8. TEXT, IMAGE, CARD 메시지 포함
9. 최근 30일을 정확히 30개 날짜로 반환
10. 활동 없는 날짜 count 0, level 0
11. 날짜 오름차순 반환
12. 날짜별 메시지 수에 맞는 level 반환
13. 최근 7일 수에 맞는 activityStatus 반환
14. Asia/Seoul 날짜 경계 검증
15. 메시지 content를 조회하지 않는 최소 projection 또는 집계 쿼리 사용
16. 데이터가 없으면 recent7DaysMessageCount = 0,
    activityStatus = INACTIVE, 모든 날짜 level 0

활동 상태 경계 테스트:

- 0 → INACTIVE
- 1, 9 → LOW
- 10, 29 → MEDIUM
- 30 → HIGH

잔디 level 경계 테스트:

- 0 → 0
- 1, 4 → 1
- 5, 9 → 2
- 10, 19 → 3
- 20 → 4
